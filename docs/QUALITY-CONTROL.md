## Invariants drive our checks

| Risk | Acceptance rule |
|---|---|
| Lost or overwritten answers | Explicit revise keeps the original sentence, manual vehicle corrections, college, type/term, start date and owned draft identity. Repeated browser Back/read keeps the latest corrections. Changed wording triggers a fresh read rather than stale-field reuse. |
| Wrong owner or campus | Protected draft state belongs to the current server-resolved demo person. Stale-person posts and foreign application IDs cannot copy a previous person's draft into another account. Selecting another college creates a separate campus-bound flow. |
| Inference replay | Successful read/compare POSTs redirect to GET pages. Normal Back/refresh does not repeat a model request or create a payment. Blank optional schedule text allows manual entry without invoking the reader. |
| Wrong fee or planning promise | Catalog and server-resolved category control integer-cent prices. AI/browser values cannot supply a fee. Missing prices stay unavailable. Confirmed visits must fit demo date rules; daily continuation starts only one first-day permit, not a bulk purchase. |
| Mismatched bound order | Once a PayPal order exists, revisions cannot change the reviewed application/vehicle snapshot beneath it. The controller returns to the existing checkout before vehicle mutation; the application service also refuses an order-bound revision. |
| Stale-tab purchase | `CheckoutReviewSnapshot` binds the rendered owner/application, campus, category, permit type/name, term, dates, integer-cent total and actual vehicle fields. SDK and redirect starts send that fingerprint; `CheckoutService.StartAsync` refreshes the facts under its write transaction and rejects a mismatch before creating a new order. This is freshness, not authorization. Order/capture/status values are excluded so unchanged retries remain valid. |
| Owner-safe rate rejection | A vehicle-reader 429 restores the current server-resolved `DraftOwner`, the owned `FlowId` and entered answers. It does not restore another person's stale draft. `Retry-After` applies before inference; retry recovery remains subject to normal owner/flow validation. |
| False payment or duplicate charge | An order/return page is not payment. Issuance requires completed capture, expected gross USD amount, saved order and capture ID. Retry/recovery reuses durable references and checks provider state before another purchase. Unapproved/declined outcomes stay unpaid. |
| Misleading UI or missing proof | Eligible official SDK options render once at the reviewed total; display alone must create no order. Failure/no-JavaScript paths remain actionable. Paid/issued history is distinct from active validity; unknown pending prices say Not priced, and genuine free/exempt records remain $0. PDFs retain matching references and later retrieval. |
| False AI success | Pinned returned model identity, strict schema, grounding, response-size and elapsed-deadline checks precede the Together label. Unusable answers use a labeled fallback. Model reasoning is not displayed, parsed as final content or logged. |

Successful model requests use the fixed HTTPS Together endpoint, low reasoning effort, temperature 1 and a 2,048-token total completion cap. The default complete-response budget is 10 seconds, configurable from 1–90 seconds; vehicle/schedule envelopes are bounded to 64/32 KiB. No model tools or payment authority are provided, and no weights are trained or fine-tuned. US development does not establish US-only processing, ZDR or verified account privacy settings.

Vehicle/chat and schedule routes share process-local limits before inference: 20/client/minute, 60 globally, two concurrent/client and four globally. A 429 includes Retry-After and retains form answers. These limits are not authentication, distributed quotas or a provider billing cap.

## How we repaired and reviewed the flow

We reproduce each concern with fictional input and expected/actual behavior, separate real defects from historical guide examples, then repair the responsible boundary. New regressions exercise explicit revise, repeated Back with a 740 → 750 correction, changed-sentence extraction, saved-review date/identity, no-JavaScript revise, change-college, stale-person rejection and order-bound snapshots. The Home role labels use the actual category resolver; both Students and Public visitors retain day and term options.

Server draft snapshots use protected Cookie TempData, compression, expiry and a bounded permit-state budget. A short owner/flow-keyed tab cache stores only editable facts, with a two-hour expiry refreshed on edits. It excludes CSRF/authentication, model provenance, application/order/capture/receipt identifiers and payment authority; it is not localStorage or a permanent profile. Blocked storage retains the server-backed explicit-revise path. Expired/evicted snapshots and combined cookie/header limits remain practical boundaries to state honestly.

We run focused checks, relevant broader suites and provider checks separately. We inspect actual rendered UI and PDF pages, reconcile agent findings, review the diff/evidence, then commit/push authorized changes and verify the remote source. After an interrupted payment check, we inspect saved/provider state before repeating a transaction.

The 21-page feedback review found repeated layout requests rather than 21 independent defects. Original orange tutorial callouts were not new complaints. Personal handwriting is kept private. The refreshed 21-page guide uses the stated baseline UI and its complete rendered PDF was visually reviewed. New unpaid applications and separate historical confirmed-payment examples are explicitly labeled. The reviewed PDF SHA-256 is `e405a9faa5002f413cc1dc6bae2ebc989816410e99fd8a8e2eaf08a80ca39028`.

## Retained repair failures and corrections

The first final-repair candidate executed 582 backend cases: 551 passed, 31 failed and zero skipped. Twenty-seven failures were direct EF Core `InvalidOperationException` results from resetting `IsLoaded` on a populated required navigation; four HTTP 500-versus-409 failures came from that same path. `repair-final.trx` and `first-final-candidate-source.json` retain the failing scope. The corrected implementation reloads the application and resolves/reloads Vehicle and PermitType by their authoritative foreign keys, assigning matching nonnull navigations; it does not reset `IsLoaded` or clear the tracker. A warm foreign-key-change regression was added.

The next backend run executed 583 cases: 582 passed, one failed and zero skipped. That remaining test expected a later `DbUpdateConcurrencyException`; the authoritative reload correctly rejected a changed $40 saved quote against the $30 catalog with `CheckoutPricingException` before any provider call. The test contract was corrected and strengthened to require zero Create/Get/Capture calls, an unchanged 4,000-cent database quote and no order ID. No production change was made for this expectation correction. The intermediate `repair-final-fixed.trx` remains a failed historical run. Only the final passing proof above counts as the current release result; these attempts are neither clean passes nor additional distinct cases. After that expectation correction, the broad verification baseline passed 583/583 backend cases at `9de5bd40f72a43565a56b5c6b6ffdceba08a41db`.
